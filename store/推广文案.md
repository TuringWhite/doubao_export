# 推广文案包

> 原则：**讲"备份我自己的聊天记录"，不要讲"爬取豆包数据"**。
> 前者是用户权利，后者会触发平台的敏感词与审核。同一个意思，两种写法，曝光量能差一个数量级。

## 二、V2EX

**节点**：分享创造

**标题**

```
[分享创造] 写了个 Chrome 扩展，把豆包的历史对话批量导出成 Markdown
```

**正文**

```
豆包没有批量导出功能，几百条对话只能一条条复制。前阵子想把它导出来整理成笔记，
手动弄了三十几条就放弃了，干脆自己写了个扩展。

做的事很简单：枚举侧边栏全部对话 → 逐条走接口分页拉全 → 每条存成一个 .md。

几个实现上踩过的坑，可能对写类似工具的人有用：

1. 侧边栏是虚拟滚动列表，滚动一次等 400ms 就判断"没新增"是错的，实测只拿到 5 条
   （实际有 570 条）。改成连续 3 轮无新增才收手，并且要滚所有可滚动子容器，
   因为真正的 scroller 是 #flow_chat_sidebar 的深层节点。
2. 角色判定踩了大坑：一开始按 user_type === 0 判断用户，结果 409 个文件里
   一条用户消息都没有，全是 AI。打印字段分布才发现 user_type 实际是 1=用户、2=助手，
   而且 bot_reply_message_id 在 300/300 条消息上都有（用户消息也带），完全没有区分度。
3. 智能体对话 /chat/bot/chat/:id 的首屏分页参数跟普通对话不一样
   （anchor=0 + direction=3 vs MAX_SAFE_INTEGER + direction=1），不单独处理会拉空。

实测 570 条对话一次导出成功，0 失败，大约 5 分钟。

代码全开源，MIT：
https://github.com/TuringWhite/doubao_export

只在自己浏览器里跑，请求只发往 doubao.com，没有后端也没有埋点——介意的话可以
自己 grep 一遍再装。
```

## 四、掘金 / CSDN（技术文）

**标题**

```
豆包历史对话批量导出：一个 Chrome MV3 扩展的完整实现
```

**大纲**

1. 背景：豆包无批量导出，手动复制的成本
2. 抓包分析：`/im/chain/single` 的请求结构与分页参数
3. 三个坑（虚拟列表枚举 / 角色字段误判 / 智能体首屏锚点）
4. MV3 实践：主世界 hook 注入、`registerContentScripts({world:"MAIN"})`、Service Worker 下载
5. 测试：9 组单测怎么在无浏览器环境下跑（vm 沙箱 + fetch stub）
6. 结论与仓库链接

> 技术文的转化率不如 V2EX，但**搜索长尾最好**：半年后还有人从"豆包 导出"搜进来。

**标题**

```
把豆包三年的聊天记录，一次性搬进了 Obsidian
```

**正文**

```

后来找了个办法：装个浏览器扩展，点一下，几百条对话全部变成 Markdown 文件，

⚠️ 数据都在自己电脑上，不上传
```

## 八、发布时机（比渠道更重要）

这类工具的流量不是"推"出来的，是"事件"带来的：

- 豆包改版 / 智能体下线 / 宣布清理数据 → 当天会有大量"怎么备份"的搜索
- AI 工具迁移潮（换 ChatGPT / Claude / Kimi）→ 迁移话题
- 自己的记录丢了 / 换电脑 → 个人痛点，小红书这类内容最容易爆

平时就是把 README 和 Release 维护好，等风来。**提前发一堆帖子，不如在事件当天发一条。**

## 九、别做的事

- ❌ 不要买 star、不要互 star 群 —— GitHub 会识别异常增长，且懂行的人一眼看出来
- ❌ 不要在任何平台写"破解""绕过限制""无视风控"
- ❌ 不要在字节/豆包相关话题下硬蹭，容易被举报
- ❌ 不要承诺"永久可用"——豆包改版就失效，这是常态
